dubbo-getty 是 Apache Dubbo 生态中的 Go 异步网络库。这里的八项贡献围绕网络库最容易出问题的边界展开：重连是否有上限、关闭是否能结束、异常路径是否释放资源，以及配置是否真正影响运行行为。

每项说明以最终合并代码为准；测试执行结果只引用 PR 中已有的验证记录。

## PR #144：整理示例错误处理与维护配置

已合并 · [原始 PR](https://github.com/apache/dubbo-getty/pull/144) · [代码变更](https://github.com/apache/dubbo-getty/pull/144/files)

### 背景

项目除了网络库本身，还包含性能分析示例、构建状态展示和自动回复配置。这些辅助内容影响使用者排障和贡献者理解项目状态。

### 问题

pprof 示例忽略了 `http.ListenAndServe` 的返回错误，端口占用等启动问题不容易被发现。仓库还保留着面向 Go 1.13 的过期构建配置，README 的状态徽章与现有构建系统不一致。

### 解决方式

为 pprof 服务记录返回错误，删除过期构建配置，将 README 徽章指向 GitHub Actions，并修正自动 Issue、PR 回复中的语法问题。对关联 Issue 中其他建议逐一核实后，将修改范围限定在有依据的维护问题上。

### 成果

示例服务出错时有可见日志，构建入口与状态展示保持一致。PR 记录了 `go test ./...`、`go vet ./...` 和差异检查通过；这一项改善的是可维护性，没有改变核心网络协议行为。

## PR #142：解除客户端关闭与重连之间的相互等待

已合并 · [原始 PR](https://github.com/apache/dubbo-getty/pull/142) · [代码变更](https://github.com/apache/dubbo-getty/pull/142/files)

### 背景

客户端关闭时需要结束所有会话，而会话关闭又可能触发重连。业务回调也可以主动调用客户端的 `Close()`，这些路径并不是彼此独立的。

### 问题

原来在持有客户端会话表锁时调用会话的 `Close()`，清理流程可能通过重连再次需要同一把锁。同步执行重连还会让关闭流程受到重试影响；如果关闭等待的工作协程正是当前回调所在协程，就会形成等待自身的死锁。

### 解决方式

在锁内取出会话表并清空客户端引用，释放锁后逐个关闭会话。会话触发重连时统一进入 `runReconnect()`，同时到来的触发通过完成通道和待处理标志合并为一个工作协程。

最终合并实现移除了客户端的 `WaitGroup` 等待：`Close()` 发出关闭信号并清理会话，重连协程自行观察关闭信号退出。关闭后的新重连请求直接完成，不再启动拨号。

### 成果

关闭会话不再发生在会话表锁内，并发重连有了统一入口，回调内关闭客户端也不再等待自身。回归测试覆盖关闭与重连交错、退避取消、并发触发合并、关闭后空操作及回调内关闭等情况。

## PR #140：让重试预算只计算失败尝试

已合并 · [原始 PR](https://github.com/apache/dubbo-getty/pull/140) · [代码变更](https://github.com/apache/dubbo-getty/pull/140/files)

### 背景

客户端需要逐步建立连接，直到连接池达到 `ConnectionNumber`，并通过 `ReconnectAttempts` 限制失败重试。

### 问题

成功增加连接也会消耗重试计数。当目标连接数大于重试次数时，即使每次连接都成功，连接池也可能提前停止补齐。部分底层拨号循环还会让失败一直停留在内部，无法由上层统一控制退出。

### 解决方式

将拨号和 `connect()` 收敛为单次尝试，由 `connect()` 返回是否真正增加了会话。上层只在失败时增加计数，成功后重置连续失败次数，再继续填充连接池；退避过程可以响应关闭信号。

例如，目标需要五条连接、最多允许三次连续失败时，五次成功连接应当全部完成，而不是在第三次成功后停止。

### 成果

连接池填充与失败预算各自符合配置语义。新增测试分别覆盖目标持续不可达时有界退出，以及 `ConnectionNumber > ReconnectAttempts` 时成功填满连接池。PR 记录了 Go 测试、静态检查与差异检查验证。

## PR #139：修正 UDP 接收缓冲区的大小计算

已合并 · [原始 PR](https://github.com/apache/dubbo-getty/pull/139) · [代码变更](https://github.com/apache/dubbo-getty/pull/139/files)

### 背景

UDP 读取前需要申请缓冲区，其大小应根据默认读取容量与配置的最大消息长度计算。

### 问题

原来的上限比较使用了尚未通过 `recv()` 填充的 `bufLen`。这一变量此时仍为零，使限制缓冲区大小的分支实际上不起作用，配置规则与真实分配脱节。

### 解决方式

抽出 `udpReadBufferLen()` 单独计算大小：非正的最大消息长度使用默认容量，正数配置按既定规则取消息长度加默认容量与两倍消息长度中的较小值。计算使用 `int64`，转换为平台 `int` 前检查上界。

### 成果

缓冲区大小不再依赖一个尚未读取的数据长度。表驱动测试覆盖未启用限制、小消息限制、默认容量和较大消息等情况，使不同配置的分配规则可以直接验证。

## PR #138：正常关闭 WSS 服务时不再 panic

已合并 · [原始 PR](https://github.com/apache/dubbo-getty/pull/138) · [代码变更](https://github.com/apache/dubbo-getty/pull/138/files)

### 背景

WS/WSS 服务使用底层 HTTP Server 处理连接。正常关闭服务器或监听器时，`Serve()` 也会返回错误值，这不一定代表服务发生故障。

### 问题

WSS 事件循环对 `Serve()` 的错误统一记录并触发 panic，导致正常停止服务器也可能被当成异常崩溃。

### 解决方式

通过 `errors.Is` 识别 `http.ErrServerClosed` 与 `net.ErrClosed`，将它们作为正常关闭路径记录日志并返回。其他未预期的 WSS 服务错误仍保留原来的日志与 panic 行为。

### 成果

正常停止与真实故障在处理上被区分开来。新增回归测试验证 WSS 服务正常关闭不再 panic，PR 中记录了 `go test ./...` 验证。

## PR #137：修复空监听器的错误回调

已合并 · [原始 PR](https://github.com/apache/dubbo-getty/pull/137) · [代码变更](https://github.com/apache/dubbo-getty/pull/137/files)

### 背景

会话在读取或解码失败后，需要通知监听器并进行关闭清理。监听器未设置时，这条错误路径也应当能够结束。

### 问题

原先使用 `s != nil || s.listener != nil` 判断是否可以回调，非空会话搭配空监听器也会进入分支。调用 `OnError` 时就会再次崩溃，后面的 `OnClose` 也存在同样风险。

### 解决方式

把错误回调的条件改为会话与监听器同时存在，并为关闭回调增加空值保护。通过回归测试直接覆盖空监听器的错误清理路径。

### 成果

清理已有读包错误时不再产生新的空指针异常。相同问题也在 Getty 仓库的 #98 中修复，两边各自保留了对应的测试。

## PR #136：补上 WebSocket 拒绝分支的连接释放

已合并 · [原始 PR](https://github.com/apache/dubbo-getty/pull/136) · [代码变更](https://github.com/apache/dubbo-getty/pull/136/files)

### 背景

WebSocket 请求先完成协议升级，再进入自连接检查。升级之后，服务器已经持有一个需要显式释放的连接。

### 问题

发现自连接时，处理函数拒绝创建会话并直接返回，却没有关闭刚刚升级的连接，造成该分支的资源泄漏。

### 解决方式

在自连接拒绝分支关闭 WebSocket。新增测试检查完整行为：升级成功、业务会话没有创建、处理结束前连接已经关闭。

### 成果

拒绝请求时，已经分配的连接资源也被释放。PR 中记录了专门的回归测试、全量 Go 测试、`go vet` 和差异检查；相同修复随后也提交到了 Getty 的 #99。

## PR #135：恢复代码格式检查工具的兼容性

已合并 · [原始 PR](https://github.com/apache/dubbo-getty/pull/135) · [代码变更](https://github.com/apache/dubbo-getty/pull/135/files)

### 背景

项目的 `make fmt` 会调用 Go 的 `modernize` 工具，将可简化的代码写法更新到当前风格。构建流程使用工具的最新版本。

### 问题

工具更新后不再接受 `-category=efaceany`，Makefile 仍使用旧参数，导致 GitHub Actions 的代码格式检查步骤直接失败。

### 解决方式

将 `fmt` 目标中的旧参数替换为当前支持的 `-any`。修改限定在 Makefile 的工具调用处，保持原有格式化目的。

### 成果

格式化命令与当前工具接口重新兼容。PR 记录了格式化、Go 测试、`go vet` 和 lint 等本地验证，解决了由参数失效导致的构建阻断。
