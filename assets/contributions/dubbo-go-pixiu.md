Apache Dubbo Pixiu 是面向多协议服务的网关。我的两项贡献分别处理路由兼容性和 OPA 策略管理的测试覆盖：一项修复真实请求的匹配行为，另一项让策略配置、认证、转发和超时可以在完整链路上得到验证。

以下依据最终代码与 PR 记录整理，测试结果来自原始贡献中的验证说明。

## PR #947：为 OPA 策略管理补齐分层与端到端测试

已合并 · [原始 PR](https://github.com/apache/dubbo-go-pixiu/pull/947) · [代码变更](https://github.com/apache/dubbo-go-pixiu/pull/947/files)

### 背景

Pixiu 的管理模块可以通过 Open Policy Agent（OPA）管理访问策略。一次策略操作会依次经过配置解析、控制器参数处理、业务逻辑、HTTP 请求和认证中间件，仅测试其中一个函数不足以覆盖实际使用过程。

### 问题

容易发生回归的地方包括：配置缺失时能否使用默认值、调用参数与配置谁优先、超时有没有传递到底层请求、404 是否按预期处理，以及管理接口是否真正执行 JWT 认证。策略更新后能否影响网关的允许或拒绝行为，也需要完整链路验证。

### 解决方式

- 配置层使用真实临时 YAML 文件，验证 OPA 段解析、时长格式、缺省配置和错误路径。
- 控制器层验证“调用参数优先于启动配置，启动配置优先于默认常量”，并覆盖空白字符清理。
- 业务层使用 `httptest.NewServer` 检查 PUT、GET、DELETE 请求、URL 规则、幂等 404 处理与超时传播。
- 路由层保留真实认证中间件，验证无令牌拒绝、参数覆盖、策略读写往返和全链路超时。
- 最终变更还加入端到端用例、运行脚本及中英文说明，覆盖允许、拒绝、默认拒绝、策略热更新和超时后拒绝访问等行为。

### 成果

这次交付建立了从配置到网关行为的多层回归保护，既能发现参数解析问题，也能发现中间件或请求链路中的集成问题。PR 的本地验证记录报告了分层测试通过；最终代码包含进一步的端到端测试入口与运行说明。

成果是验证能力和回归覆盖的完善，不代表新增了一套策略管理业务接口。

## PR #922：恢复通配方法路由的匹配语义

已合并 · [原始 PR](https://github.com/apache/dubbo-go-pixiu/pull/922) · [代码变更](https://github.com/apache/dubbo-go-pixiu/pull/922/files)

### 背景

路由配置中的 `methods: ["*"]` 表示接受任意请求方法。RouteSnapshot 重构后，路径索引改为按方法分别保存 trie，查询路径也需要理解通配方法。

### 问题

如果查询只访问具体方法对应的 trie，就找不到放在 `MethodTries["*"]` 中的路由。结果是原来可用的通配配置出现“route not found”，影响非 HTTP 场景，也影响显式使用通配方法的 HTTP 路由。

### 解决方式

在 `MethodAllowed` 中把 `*` 识别为任意方法匹配。在 `RouteByPathAndName` 与普通路由查询中，先查具体方法的 trie；不存在或路径未命中时，再查通配 trie。通过 `matchInTrie` 集中处理查找结果，保持具体方法优先。

例如，同一路径既有 GET 专用路由又有通配路由时，GET 仍使用专用配置；专用索引未命中的路径才继续寻找通配配置。

### 成果

恢复了通配方法原有的行为，同时保留具体路由的优先级。新增测试覆盖非 HTTP 与 HTTP 请求、具体方法未命中后的回退、具体方法优先和 `MethodAllowed` 判断。PR 中记录已有测试通过，修复范围限定在查询层，没有改动 trie 包或快照构建流程。
